# Longwave KVM dongle — USB serial protocol v1

This is the normative description of the link between the Mac and the dongle.
It is written so a Swift implementation can be produced from this document
alone, without reading the firmware.

The reference implementation is [`tools/kvmctl.py`](tools/kvmctl.py).

---

## 1. Physical link

| | |
|---|---|
| Transport | USB CDC serial via the board's CH340 USB-UART bridge |
| Device path | `/dev/cu.usbserial-*` on macOS (see README for how to pick one) |
| Baud | **460800**, 8N1, no flow control |
| Direction | full duplex; the dongle may send unsolicited frames at any time |

> **Why not 921600.** The firmware was written for 921600 and the ESP32 side
> handles it, but the CH340 bridge on this board cannot sustain it through
> macOS's `AppleUSBCHCOM` driver — `esptool -b 921600` fails to verify the
> flash connection and a 921600 read of the boot log is pure noise, while
> 460800 is clean. If a future board uses a native-USB ESP32 (S3/C3/C6) or a
> CP210x, raise `KVM_UART_BAUD` in `main/kvm_config.h` **and**
> `CONFIG_ESP_CONSOLE_UART_BAUDRATE` in `sdkconfig.defaults` together.

### 1.1 The firmware log shares this UART

The ESP-IDF console writes plain-text log lines to the same UART at the same
baud. A reader **must** tolerate this:

* Log output is ASCII, so it can never contain the `0xA5` start byte.
* Any byte received outside a frame is log text and must be discarded (or
  surfaced as diagnostics), not treated as an error.
* A parser must resynchronise by scanning for `0xA5`.

Immediately after a reset, the ESP32 mask-ROM bootloader emits about 1 KB at a
fixed 115200 baud, which reads as garbage at 460800. Discard it.

## 2. Frame format

```
 byte   0      1       2         3 .. 3+LEN-1      3+LEN
      +------+------+-------+--------------------+-------+
      | 0xA5 | TYPE |  LEN  |     PAYLOAD        | CRC8  |
      +------+------+-------+--------------------+-------+
```

| field | size | meaning |
|---|---|---|
| `SOF` | 1 | always `0xA5` |
| `TYPE` | 1 | command or response code (§3, §4) |
| `LEN` | 1 | payload length, `0 … 64`. A value above 64 means this was not a frame |
| `PAYLOAD` | `LEN` | command-specific, little-endian throughout |
| `CRC8` | 1 | checksum over `TYPE`, `LEN` and `PAYLOAD` — **not** over `SOF` |

Total frame size is `LEN + 4`, maximum 68 bytes.

### 2.1 Checksum

CRC-8/ATM: polynomial `0x07`, initial value `0x00`, input and output not
reflected, no final XOR.

```swift
func crc8(_ bytes: [UInt8]) -> UInt8 {
    var crc: UInt8 = 0
    for byte in bytes {
        crc ^= byte
        for _ in 0..<8 {
            crc = (crc & 0x80) != 0 ? (crc << 1) ^ 0x07 : (crc << 1)
        }
    }
    return crc
}
```

Test vectors (generated by the reference client and accepted by the board):

| frame | bytes |
|---|---|
| `PING`, no payload | `A5 01 00 15` |
| `GET_STATUS` | `A5 02 00 2A` |
| `RELEASE_ALL` | `A5 07 00 6B` |
| `KEY_REPORT`, "a" down | `A5 03 08 00 00 04 00 00 00 00 00 DD` |

### 2.2 Parsing rules

1. Scan forward until a `0xA5` byte.
2. Read `TYPE` and `LEN`. If `LEN > 64`, discard that `0xA5` and go to 1 —
   it was log text, not a frame.
3. Read `LEN` payload bytes and one checksum byte.
4. If the checksum does not match, discard the frame and go to 1. The dongle
   will have answered with `NACK`/`BAD_CHECKSUM` for host→dongle corruption;
   for dongle→host corruption the host should just drop the frame.

## 3. Commands (host → dongle)

Every command is answered by exactly one `ACK`, `NACK` or `STATUS` frame.
Commands are processed strictly in order.

| code | name | payload | length |
|---|---|---|---|
| `0x01` | `PING` | arbitrary, echoed back | 0–63 |
| `0x02` | `GET_STATUS` | — | 0 |
| `0x03` | `KEY_REPORT` | raw 8-byte keyboard report | 8 |
| `0x04` | `MOUSE_MOVE` | `dx:i16, dy:i16, buttons:u8, wheel:i8, pan:i8` | 7 |
| `0x05` | `MOUSE_BUTTONS` | `buttons:u8` | 1 |
| `0x06` | `CONSUMER` | `usage:u16, pressed:u8` | 3 |
| `0x07` | `RELEASE_ALL` | — | 0 |
| `0x08` | `FORGET_BONDS` | — | 0 |

A command whose length does not match the table is answered with
`NACK`/`WRONG_LENGTH`; an unknown `TYPE` with `NACK`/`UNKNOWN_COMMAND`.

### 3.1 `0x03 KEY_REPORT`

The payload is the standard boot-protocol keyboard report, relayed verbatim as
HID report ID 1:

| offset | meaning |
|---|---|
| 0 | modifier bitmap |
| 1 | reserved, send `0x00` |
| 2–7 | up to six simultaneous HID usage IDs (Usage Page 0x07), `0x00` = empty |

Modifier bits: `0x01` LeftCtrl, `0x02` LeftShift, `0x04` LeftAlt,
`0x08` LeftGUI (Command), `0x10` RightCtrl, `0x20` RightShift,
`0x40` RightAlt, `0x80` RightGUI.

The dongle is **stateless** about keys: it sends exactly what it is given. A
keypress is two frames — the report with the key set, then a report of zeros to
release it. Holding all-zero for 8 ms is enough in practice.

If more than six non-modifier keys would be down at once, that is the host's
problem to solve (send `0x01` in a key slot for `ErrorRollOver` if you want to
signal it; the firmware does not).

### 3.2 `0x04 MOUSE_MOVE`

| offset | type | meaning |
|---|---|---|
| 0–1 | `int16` LE | relative X, positive = right, range −32767…32767 |
| 2–3 | `int16` LE | relative Y, positive = **down** |
| 4 | `uint8` | button bitmap held during the move |
| 5 | `int8` | vertical wheel, positive = scroll up, −127…127 |
| 6 | `int8` | horizontal pan (AC Pan), positive = right |

Button bits: `0x01` left, `0x02` right, `0x04` middle, `0x08` button 4,
`0x10` button 5. Bits above `0x1F` are ignored.

This is one HID report ID 2 — movement, buttons, wheel and pan all travel in
the same report, so a drag is "move with the button bit set", not a separate
command.

### 3.3 `0x05 MOUSE_BUTTONS`

Shorthand for `MOUSE_MOVE` with zero deltas. Sends the button bitmap with no
movement. A click is two frames: the mask, then `0x00`.

### 3.4 `0x06 CONSUMER`

| offset | type | meaning |
|---|---|---|
| 0–1 | `uint16` LE | Consumer Page (0x0C) usage ID |
| 2 | `uint8` | non-zero = press, zero = release |

A release sends usage `0x0000` regardless of the usage field. Usages above
`0x03FF` are rejected with `NACK`/`BAD_PAYLOAD`, because the report descriptor
declares a logical maximum of `0x03FF`.

Useful usages: `0x00CD` play/pause, `0x00B5` next track, `0x00B6` previous
track, `0x00E9` volume up, `0x00EA` volume down, `0x00E2` mute,
`0x0223` AC Home, `0x0224` AC Back.

### 3.5 `0x07 RELEASE_ALL`

Sends, in order: an all-zero keyboard report, a mouse report with no buttons
and no movement, and consumer usage `0x0000`. Send this when the Mac app loses
focus or exits, so nothing is left stuck down on the headset.

The `ACK` reports the *first* failure among the three, if any.

### 3.6 `0x08 FORGET_BONDS`

Erases every stored bond from NVS and disconnects. The `ACK` is sent **before**
the bonds are cleared, so the host reliably sees the answer to the command it
issued; `EVENT/DISCONNECTED` and `EVENT/ADVERTISING` follow.

This only clears the *dongle's* half of the bond. The headset must also be told
to "Forget This Device", or it will keep trying to reconnect with a key the
dongle no longer holds.

## 4. Responses (dongle → host)

| code | name | payload |
|---|---|---|
| `0x81` | `ACK` | `cmd:u8` followed by command-specific data |
| `0x82` | `NACK` | `cmd:u8, error:u8` |
| `0x83` | `STATUS` | 16-byte status block (§4.2) |
| `0x85` | `EVENT` | `event:u8` followed by event-specific data (§4.3) |

`ACK` for `PING` carries `[0x01]` plus the echoed ping payload. For every other
command it is just `[cmd]`.

`EVENT` frames are **unsolicited** and may arrive between a command and its
answer. A client must queue or dispatch them separately rather than mistake
one for a reply.

### 4.1 Error codes

| code | name | meaning |
|---|---|---|
| `0x01` | `BAD_CHECKSUM` | the CRC did not match; the payload was not acted on |
| `0x02` | `WRONG_LENGTH` | payload length does not match the command |
| `0x03` | `UNKNOWN_COMMAND` | unrecognised `TYPE` |
| `0x04` | `NOT_CONNECTED` | no host is connected, or the link is not yet encrypted |
| `0x05` | `NOT_SUBSCRIBED` | connected, but the host has not enabled notifications for that report |
| `0x06` | `TX_FAILED` | the BLE notify failed |
| `0x07` | `BAD_PAYLOAD` | payload is well-formed but out of range |

`NOT_CONNECTED` and `NOT_SUBSCRIBED` are normal, expected conditions, not
faults — the Mac app should surface them as "headset not connected" rather
than as an error.

### 4.2 Status block

16 bytes, returned by `GET_STATUS` in a `STATUS` frame.

| offset | type | meaning |
|---|---|---|
| 0 | `u8` | protocol version (currently `1`) |
| 1 | `u8` | firmware major |
| 2 | `u8` | firmware minor |
| 3 | `u8` | firmware patch |
| 4 | `u8` | link state (§4.2.1) |
| 5 | `u8` | flags (§4.2.2) |
| 6 | `u8` | number of bonds stored |
| 7 | `u8` | last keyboard LED bitmap written by the host |
| 8–13 | `u8[6]` | BLE identity address, **little-endian** (byte 13 is printed first) |
| 14–15 | `u16` LE | uptime in seconds, wraps at 65536 |

#### 4.2.1 Link state

| value | name | meaning |
|---|---|---|
| `0` | `IDLE` | radio up but neither advertising nor connected |
| `1` | `ADVERTISING` | discoverable, waiting for a host |
| `2` | `CONNECTED` | connected but not yet encrypted; input is refused |
| `3` | `READY` | connected and encrypted; input will be relayed |

#### 4.2.2 Flags

| bit | meaning |
|---|---|
| `0x01` | connected |
| `0x02` | link encrypted |
| `0x04` | advertising |
| `0x08` | at least one bond is stored |
| `0x10` | host has subscribed to the keyboard report |
| `0x20` | host has subscribed to the mouse report |
| `0x40` | host has subscribed to the consumer report |

Input is only accepted when bits `0x01`, `0x02` and the relevant subscription
bit are all set. Keyboard LEDs (bit 7 of the block) reflect Caps Lock and
friends as the headset reports them: `0x01` Num Lock, `0x02` Caps Lock,
`0x04` Scroll Lock, `0x08` Compose, `0x10` Kana.

### 4.3 Events

| code | name | payload |
|---|---|---|
| `0x01` | `BOOT` | `proto:u8, major:u8, minor:u8, patch:u8` |
| `0x02` | `ADVERTISING` | — |
| `0x03` | `CONNECTED` | — |
| `0x04` | `ENCRYPTED` | `bonded:u8` |
| `0x05` | `DISCONNECTED` | `reason:u8` (low byte of the HCI reason) |
| `0x06` | `LED_STATE` | `leds:u8` |
| `0x07` | `SUBSCRIBED` | `bitmap:u8` — bit 0 keyboard, bit 1 mouse, bit 2 consumer |

`BOOT` is emitted once at startup. Seeing it unexpectedly means the dongle
reset — for example because the host opened the serial port, which toggles
DTR/RTS and reboots the board. A client should re-read `GET_STATUS` after any
`BOOT`.

## 5. HID reports on the wire

For reference; a host implementation does not need this, but it explains what
the headset receives.

| report ID | direction | bytes | layout |
|---|---|---|---|
| 1 | input | 8 | modifiers, reserved, keycode[6] |
| 1 | output | 1 | 5 LED bits + 3 bits padding |
| 2 | input | 7 | buttons(5 bits)+pad(3), X `i16`, Y `i16`, wheel `i8`, pan `i8` |
| 3 | input | 2 | one 16-bit Consumer usage |

The full descriptor is `main/hid_report_map.h`, 173 bytes. **It must not
change** without re-pairing — see the comment at the top of that file.

## 6. Recommended client behaviour

* Open the port, wait ~300 ms for the board to finish rebooting (opening the
  port resets it), flush input, then `GET_STATUS`.
* Treat a `PING` round trip as the liveness check. Measured on real hardware:
  median 2.8 ms, p95 3.0 ms, ~340 command round trips per second.
* Coalesce pointer motion. One `MOUSE_MOVE` per input event is fine at typical
  rates, but do not queue faster than the link drains — the deltas are `int16`,
  so accumulating several events into one frame is lossless.
* Send `RELEASE_ALL` on teardown, and on `EVENT/DISCONNECTED`.
* Never assume a command succeeded without reading its answer; `NOT_CONNECTED`
  is the normal state whenever the headset is asleep or out of range.
