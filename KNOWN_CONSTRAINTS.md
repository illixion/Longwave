# Known Constraints & Gotchas

## VNC

- **8-bit color depth is broken** with most modern VNC servers (including macOS Screen Sharing). It creates a palettized color map mode (`trueColor: false`) that Tight and ZRLE encodings reject. Low quality uses 16-bit instead.
- **RoyalVNCKit's clipboard monitor is disabled on iOS** (local patch in `VNCConnection+ClipboardMonitor.swift`). Upstream polls `UIPasteboard.general` every 0.5 s and reads `.string` after every changeCount bump; since iOS 16 each such read the user did not initiate raises the "Longwave would like to paste from …" banner, which showed up every time the software keyboard was raised over a VNC session. visionOS never hit it because that code is `#if os(iOS)`, which excludes visionOS — the headset has never had client→server clipboard. Server→client still works (writing the pasteboard prompts nothing) and the keyboard grid's paste key still reads on demand, where the prompt is the user's own action.
- **iOS stream chrome hides while typing.** The keyboard shrinks the stream's GeometryReader, so the desktop refits above the keys — and the bottom capsule then sat exactly where a macOS login window keeps its password field. While the modifier strip is up it is the chrome; the capsule returns when the keyboard is dismissed.
- **RoyalVNCKit carries local modifications** — static linking (dyld crash fix), JPEG quality/compression settings, framebuffer pause/resume, no clipboard polling on iOS. The gitignored `repos/royalvnc` checkout is the working copy; the committed source of truth is `ci/patches/royalvnc-longwave.patch`. **Re-export the patch after any change to `repos/royalvnc`** (`cd repos/royalvnc && git diff 337197a > ../../ci/patches/royalvnc-longwave.patch`), otherwise CI release builds break.

## Moonlight

- **C callbacks fire on background threads** — renderers use `nonisolated(unsafe)` state and `@unchecked Sendable` conformance. Each linked copy of the library holds its own renderer/delegate references (`MoonlightLibrary`), which the copy's callbacks read.
- **moonlight-common-c is single-connection by design, so the app links it three times.** Every `Li*` call drives one set of globals (`StreamConfig`, callbacks, depacketizer state, worker threads); there is no handle. To stream from more than one host at once the package vends `MoonlightCommonC1`/`MoonlightCommonC2`: the same sources compiled again with every external symbol renamed by `#pragma redefine_extname` (`ci/deps/moonlight-common-c/ml_redefine_symbols.h`, laid out by `make-instances.sh`). Three traps: (1) a symbol missing from the list does **not** fail the link — the archive member found first wins and one copy starts writing the other's globals — so run `scripts/verify-moonlight-instances.sh` (CI does) and `--regenerate` the list after bumping the dependency ref; (2) the copies must not redeclare `Limelight.h`'s types or function names — Clang merges textually identical C declarations across modules, Swift then attributes the structs to whichever module loaded last (`MemberImportVisibility` errors), and the renamed functions can resolve to the wrong copy — so each copy's public header declares only `mlN_Li…` prototypes with `void*` params and an asm label (`__asm__("mlN_LiStartConnection")`, literal, because `redefine_extname` emits no leading underscore); (3) enet is compiled *into* each copy, with a header copy that has no module map — Xcode's explicit-modules C builds would otherwise import the original `enet` module and undo the rename. One `MoonlightConnectionManager` per copy, owned by `MoonlightSessionStore`; the stream/keyboard `WindowGroup`s are value-keyed by `MoonlightSessionID`. Shared physical inputs (GameController pads, `GCMouse`, `GCKeyboard`) are app-wide, so they go only to the session holding `MoonlightInputFocus`, claimed by the stream the user looks at (visionOS) or points at (macOS).
- **CryptoManager builds X.509 certs from scratch** using ASN.1 DER helpers (no OpenSSL). The cert, private key (Keychain), and PKCS#12 are cached in UserDefaults. If the Keychain is reset, the client identity is regenerated and all servers must be re-paired.
- **NvHTTPClient uses NWConnection, not URLSession** — required for self-signed cert acceptance and mutual TLS. HTTP/1.1 is manually constructed. Responses are XML parsed with Foundation's `XMLParser`.
- **Server cert and UUID are stored in UserDefaults**, keyed per server — SwiftData doesn't handle raw `Data` blobs well for binary cert data.
- **Opus multistream decoder** requires channel count, stream count, coupled stream count, and channel mapping from the `OPUS_MULTISTREAM_CONFIGURATION` provided by moonlight-common-c. The decoder is always created even in muted mode (C API requirement), but AVAudioEngine is skipped.
- **Video renderer uses AVSampleBufferDisplayLayer** via `UIViewRepresentable` (`VideoLayerView`). The layer handles hardware decoding and display internally, including native HDR/EDR tone mapping. The custom UIView subclass overrides `layoutSubviews()` to keep the layer frame in sync — setting the frame in `makeUIView` alone doesn't work because `bounds` is zero at that point.
- **AV1 uses a custom OBU parser** (`BitstreamReader` + `parseAV1SequenceHeader`) to extract sequence headers for `CMVideoFormatDescription` creation. The parser implements AV1 spec Section 5.5 at bit granularity. AV1 config records (`av1C`) are built per ISO 14496-12.
- **HDR metadata uses raw memory access** to read `SS_HDR_METADATA` because Swift cannot directly access the anonymous struct array `displayPrimaries[3]` from the C header. The `packHdrMetadata` method reads fields at known offsets via `UnsafeRawPointer.bindMemory`. MDCV is packed in GBR order (not RGB) per the MDCV spec. Format description extension keys must use the proper CoreMedia constants (`kCMFormatDescriptionExtension_MasteringDisplayColorVolume`, `kCMFormatDescriptionExtension_ContentLightLevelInfo`) — lowercase string literals are silently ignored.
- **Audio FEC patches are required** — without the CI patches, moonlight-common-c crashes on FEC recovery with newer Sunshine versions. Always apply patches from `ci/patches/` when setting up the dependency.
- **Pairing supports two hash variants** — SHA-256 for server generation >= 7 (modern Sunshine), SHA-1 for older servers. The `NvPairingManager` auto-detects based on `/serverinfo` response.

## Audio Streaming

- **`ConnectionType.audio` is not gated** behind a compilation condition (unlike `.moonlight`) — it has no external dependencies.
- The macOS target shares the visionOS target's Swift settings (`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`); `Shared/` types are declared `nonisolated` so they're usable from audio/network threads in both targets.
- **The receiver has two session modes** (`AudioMode`, toggled in the mini player). **Speaker** (default): a **mixable** session (`.playback` + `.mixWithOthers`, spatial `.bypassed`, `setIsNowPlayingCandidate(true)`) — coexists with other apps/VoIP, never interrupts, and **auto-reloads** (fresh receiver) when another app grabs the audio config. It's ineligible for Now Playing/Control Center, so **don't add `MPNowPlayingInfoCenter`/`MPRemoteCommandCenter` to Speaker mode** — it would force an interrupting session. **Music**: an **exclusive** session (no `.mixWithOthers`) that *is* a Now Playing app — `MPNowPlayingInfoCenter` + `MPRemoteCommandCenter` map Control Center transport to the Mac's Music.app, and on interruption (a call) it **pauses the Mac source + local playback** (sends `.pause`) and resumes on `.shouldResume`, instead of reloading. The mode is passed into `AudioStreamReceiver`; changing it mid-stream rebuilds the receiver (the session category differs).
- **VoIP calls steal the audio session** (e.g. Google Meet in Safari): interruption *began* fires when the call starts (no ended/route-change until it finishes) and playback dies silently while TCP keeps flowing. Engine-only rebuilds do NOT recover — only a fresh receiver that re-asserts `setCategory`/`setActive` does. The receiver observes interruption (began+ended), `AVAudioEngineConfigurationChange`, and the silence-secondary-audio hint, and emits `.reloadRequested` → the manager reconnects immediately (loop guard: a second reload within 2 s falls back to backoff retry). Configure the session **once per receiver** — re-asserting it mid-call breaks the call's audio.
- **`setActive(true)` on every engine build** — after an interruption the session is deactivated; `engine.start()` alone reports running but pumps audio nowhere.
- **Now playing is read system-wide, not from Music.app.** `NowPlayingCoordinator` prefers `MediaRemoteBridge` (every player — Apple Music streaming, Spotify, browser video — with artwork) and falls back to `MusicAppBridge`'s AppleScript. The AppleScript path remains as the fallback because it uses nothing private, but it sees only Music.app and **`artwork 1 of current track` is empty for anything streamed from Apple Music** (only local/downloaded files have it) — which is why the MediaRemote path exists. Arbitration is on *content*: whichever backend actually reports a track wins, because with nothing playing a working-but-idle MediaRemote and a broken one are indistinguishable.
- **Now-playing artwork is not necessarily square, and its MIME type lies.** Once video counts as now playing, artwork has the video's aspect ratio — a browser reports 336×188 for 16:9 where Music.app reports 600×600 — so the artwork pane takes the art's own shape (`AudioPlayerPanel.artworkHeight`, capped at square so portrait art pillarboxes rather than growing the window). Window hosts reserve `AudioPlayerPanel.topSlack` *outside* their glass, in a `.plain` window that draws its own `glassBackgroundEffect` — so total window height is constant while the panel appears to grow and shrink at its top edge only, and nothing below the art moves. **visionOS anchors a window's centre when its content size changes** (measured in the simulator: a 175pt content change moved the top up 118px and the bottom down 120px), so simply letting a `.contentSize` window resize makes the transport controls drift; and a fixed square pane instead leaves a tall slab of visible glass. Beware too that a `.fill` image *reports a size larger than its container*, so putting one behind a `.fit` copy in one `ZStack` makes the stack adopt the wider size and re-propose it to the fit copy, which then fills and crops. Separately, MediaRemote declares `image/jpeg` for what is actually **uncompressed TIFF** (a 336×188 "JPEG" arrived as 256 KB) — don't trust `artworkMIME`; `NSImage` sniffs the real format and `NowPlayingArtwork` re-encodes, bounding only the longest side so the ratio survives.
- **MediaRemote transport commands need the runloop to spin before the sender exits.** `MRMediaRemoteSendCommand` returns true once the request is *queued* — it dispatches asynchronously over XPC to `mediaremoted` — so `_exit()` straight afterwards drops the message and the command silently does nothing, while still reporting success and a clean exit status. The one-shot send path therefore keeps the runloop alive for `kSendFlushSeconds` (0.75s; 1.2s was observed to work, 0 to fail). Related: `MediaRemoteBridge.send` is `async` and waits for the helper's exit status, because "the process launched" is not evidence the command worked — that assumption is precisely what hid a dead play button. Transport routing lives in `NowPlayingCoordinator.send`: MediaRemote when it actually has a track (so play/pause reaches Spotify or a browser), otherwise AppleScript against Music.app, which is also the only backend that can start playback when **nothing** is playing — MediaRemote has no Now Playing app to command then and no-ops. Note `MusicAppBridge.send` deliberately never launches Music, so an idle Mac with Music quit stays idle.
- **The MediaRemote helper must be entered as an XS sub, not from a library constructor.** Since macOS 15.4 `MediaRemote.framework` answers only processes whose signing identifier starts with `com.apple.`, so the read happens inside `/usr/bin/perl` (`com.apple.perl`), which loads `longwave-mediaremote.dylib` — Longwave never loads it or links MediaRemote. The trap: the entry point has to run **after `dl_load_file` returns** (via `dl_install_xsub`). From a constructor, dyld still holds the loader lock, MediaRemote's reply path lazily loads more images, and **every completion block deadlocks and never fires** — which looks exactly like a permission failure, right down to `mediaremoted` logging the request succeeding in under a millisecond. `MRMediaRemoteGetNowPlayingApplicationIsPlaying` keeps working throughout, making it look like only metadata is withheld. Full write-up in [[MediaRemoteHelper/README.md]].
- **Audio-session / window-lifecycle changes can only be verified on device** — build, then commit right away; on-device testing happens after the commit, and a bad change is reverted rather than held back. Call out what to test on the Vision Pro in the commit summary.

## Native Mac Streaming

- **Transparent desktop capture is a window composition, not a display capture.** `MacNativeScreenCapture` includes visible layer-zero application windows over a clear ScreenCaptureKit background, which removes wallpaper without color keying and preserves translucent pixels correctly. A raw display capture is already flattened against its wallpaper; green-screen subtraction cannot recover correct RGB behind translucent windows.
- **Menus, Dock, Menu Bar, popovers, Mission Control, Notification Center, and higher-layer utility surfaces are not captured in Unity's first milestone.** Unity starts with only its control window and the desktop stream off. Unity Controls can show/hide all or individual layer-zero application windows, persist an opt-in auto-show policy, and show the full desktop on demand. The Companion caps simultaneous per-window ScreenCaptureKit/VideoToolbox pipelines at six.
- **VideoToolbox's alpha encoder selector and its emitted format subtype differ.** The compression session is created with `kCMVideoCodecType_HEVCWithAlpha` (`muxa`), but encoded samples carry an `hvc1` format description with `kCMFormatDescriptionExtension_ContainsAlphaChannel = true`. The receiver must validate that extension rather than require a `muxa` subtype.
- **There is no 4:4:4 HEVC on Apple platforms.** VideoToolbox exposes exactly five HEVC profile-level constants — `Main`, `Main10`, `Main42210`, `Monochrome`, `Monochrome10` — so the chroma ladder for an HEVC stream is 4:2:0, 4:2:0 10-bit, or 4:2:2 10-bit, full stop. `Main42210` genuinely produces 4:2:2 (verified by parsing `chroma_format_idc` out of the emitted SPS: `profile_idc=4, chroma=2, bitDepth=10`) and encodes on the media engine from plain BGRA input, so no capture-side pixel-format change is needed for it.
- **4:2:2 is negotiated, never assumed.** No API answers "can you hardware-*decode* Main42210" — `VTIsHardwareDecodeSupported` is per codec, not per profile. So the viewer probes itself (`MacNativeVideoCapability`): it builds a real 4K Main42210 format description from parameter sets lifted from VideoToolbox's own encoder and asks for a decompression session with `RequireHardwareAcceleratedVideoDecoder`. The answer rides in `Hello.decodesHEVC422`, and a host that hears nothing sends 4:2:0 — so the worst case of a wrong probe is the previous behaviour, never a software-decoded Retina desktop. Note the **simulator has no hardware video decoder at all** (`VTIsHardwareDecodeSupported(HEVC)` is false there), so a simulator client always negotiates 4:2:0; only a real headset can answer for the headset.
- **Ask for the hardware encoder explicitly, then check you got it.** `VTCompressionSessionCreate` with a nil encoder specification may hand back a software encoder. `MacHEVCEncoder` requires hardware first, retries without the requirement only so a Mac with no hardware HEVC encoder still works at all, and reads `UsingHardwareAcceleratedVideoEncoder` back afterwards — asking and receiving are different questions. The companion's Screen Status pane reports the result, because nothing about the picture reveals which encoder or chroma format is in use.
- **Every stream's coordinates are pixels, not points.** Both the desktop and per-window streams capture at the source's native backing scale, so on a Retina Mac a stream coordinate is twice the `CGEvent` point coordinate. The host divides by the stream's pixels-per-point (`SCContentFilter.pointPixelScale`, or the reduced scale when a display's long edge is pulled back under 4096 px) before injecting. Skipping the divide is not a uniform offset — it is a 2x error that grows with distance from the display's origin, so it looks fine near the top-left and badly wrong in the opposite corner.
- **Transport the exact CoreMedia ImageDescription.** Reconstructing only VPS/SPS/PPS can drop the alpha auxiliary-layer metadata. The protocol sends `CMVideoFormatDescriptionCopyAsBigEndianImageDescriptionBlockBuffer` output and reconstructs it with `CMVideoFormatDescriptionCreateFromBigEndianImageDescriptionData`.
- **Physical Vision Pro testing is required to prove final compositing.** Simulator/device builds verify the API surface, but only the headset can prove that `AVSampleBufferVideoRenderer` preserves decoded alpha through the plain SwiftUI window, including rounded corners, shadows, and vibrancy. This now applies to **per-window** streams only — the desktop stream is the host's whole display, captured and encoded opaque (`kCMVideoCodecType_HEVC`), so there is no alpha in it to preserve. `HelloAck.supportsTransparentDesktop` is `false` on every host and survives only so older clients still decode the ack.
- **Exactly one authenticated viewer is allowed.** A candidate replaces the current viewer only after TLS authentication and a valid hello, receives the current format description, and causes the previous viewer to receive a named replacement frame before disconnect. The Mac posts a notification naming the new viewer and any displaced viewer.
- **The current security transport is TLS 1.2 external PSK, domain-separated from audio and injection while reusing the companion token.** Network.framework's external-PSK path does not reliably negotiate TLS 1.3. Migration to TLS 1.3 pinned identities remains isolated behind `MacNativeStreamCrypto`.
- **LAN-first, manual addressing for now.** The Mac advertises `_longwave-native._tcp` on port 4857 and both targets declare the Bonjour service, but the connection form does not yet browse/select services. A LAN IP/hostname is entered manually; a Tailscale address also works.
- **Protocol v2 is negotiated, not assumed.** A hello without `protocolVersion` gets the v1 behavior (one anonymous desktop stream, legacy frames); a v2 `helloAck` is a JSON capability payload (platform, key-code space, window-stream support). Stream ID 0 is the whole-desktop stream in the multiplexed (`window*`) frames; real CGWindowIDs/HWNDs are never 0.
- **Per-window streams end when the window leaves the screen.** ScreenCaptureKit's shareable content only lists on-screen windows, so minimizing (or moving to another Space) closes that stream with a `windowClosed` frame and the visionOS scene dismisses itself. The 1 s inventory poll is also what tracks resizes (stream reconfigures; encoder re-emits a format on the new dimensions).
- **Per-window input must raise the window first.** `CGEvent` mouse events are routed by *screen position*, not window, so a click on an occluded streamed window would land on whatever covers it. The companion raises the target (app activation + AX raise matched by frame, then title — there is no public CGWindowID→AXUIElement bridge) before injecting when it isn't topmost at that point. Same story on Windows with `SendInput` + `SetForegroundWindow` (with the `AttachThreadInput` foreground-lock workaround).
- **Windows hosts speak the same protocol with three deliberate differences**: opaque HEVC (no alpha — format kind `hevcParameterSets`, Annex-B VPS/SPS/PPS + 4-byte length-prefixed sample NALs, rebuilt client-side via `CMVideoFormatDescriptionCreateFromHEVCParameterSets`); `keyCodeSpace: hidUsage` (the client sends raw HID usages instead of kVK codes; the modifier mask is ignored — modifiers arrive as their own key events); and remote control defaults **on** (the paired token is the consent gate; there is no macOS-Accessibility-style second gate).
- **BouncyCastle TLS-PSK server + Apple client: refuse certificate status.** SChannel has no PSK suites, so the Windows server handshakes with BouncyCastle — whose `AbstractTlsServer` echoes a client's `status_request` (OCSP) extension even in a PSK handshake. Apple's TLS rejects that ServerHello with `decode_error` (no Certificate message can follow); OpenSSL tolerates it, so only an Apple-client test catches it. `AllowCertificateStatus()`/`AllowMultiCertStatus()` must return false.
- **Audio is a macOS-only capability and the handshake says so.** `helloAck.supportsAudioStream` tells the headset whether this host also serves the companion audio stream; Windows sends false and the Native window disables its Audio toggle with an explanation. The field is optional so hosts that predate it still decode — absent means "macOS yes, anything else no". Without it a Windows connection leaves the audio player on "Connecting…" forever, because nothing is listening on the audio port.
- **Releasing a D3D11 stream does not release its memory — the device has to go.** D3D11 defers destruction while the immediate context still references the textures last copied, so disposing the capture and encoder leaves the allocations alive: measured at ~150 MB of GPU memory and ~290 MB of private bytes still resident long after the viewer left, against a 17 MB idle baseline. Teardown must `ClearState()` + `Flush()` the context and then dispose the device (lazily rebuilt on the next subscription). Two traps: Vortice **caches** the `ImmediateContext` wrapper on the device (`ImmediateContext__`), so a pipeline must *not* dispose the context it borrowed — that would break every other pipeline; and `IDirect3DDevice`, the WinRT wrapper, holds its own reference, so nulling the field without disposing it keeps the real device alive until a finalizer happens to run. This applies when the last subscription stops too, not just on disconnect — a connected viewer with Screen off is the common idle case.
- **The MF Video Processor's D3D sample allocator starves under downstream backpressure** (`ProcessInput` → `MF_E_NOTACCEPTING` once its output samples are held). The Windows pipeline avoids it where possible — NVIDIA's HEVC MFT accepts ARGB32 directly, bypassing the converter — and otherwise copies converter output into an owned NV12 ring and releases the converter's sample immediately. Windows.Graphics.Capture also fires at *composition* rate (200+ fps on high-refresh monitors), so `Submit` caps at the encoder's declared 60 fps.

## Broadcast

- **visionOS strips the AVCapture surface**: no `AVCaptureAudioDataOutput` (mic uses an `AVAudioEngine` input tap), no session presets (device native format only), no `AVCaptureVideoPreviewLayer` (preview is an `AVSampleBufferDisplayLayer` fed raw capture frames marked `DisplayImmediately`).
- **"Mirror My View" is not a capture device** — it only reaches third-party code through a ReplayKit broadcast upload extension via the system View Sharing menu. Device discovery only ever returns the Persona "Front Camera".
- The extension bundle id (used by `RPSystemBroadcastPickerView`) is **derived** in `BroadcastShared.extensionBundleID` as `Bundle.main.bundleIdentifier + ".broadcast"`, matching the target's `$(LONGWAVE_BUNDLE_ID).broadcast`. Do not put a literal back: the app's id differs per edition (`pro.longwave.oss` vs `pro.longwave.app`), so a constant would be right for one and silently wrong for the other — the picker opens with nothing preselected rather than failing visibly.
- Both the app and extension have `.entitlements` files with the `group.pro.longwave` App Group — but **the effective group is resolved at runtime** (`BroadcastShared.appGroup`): sideload re-signing (`build-and-sign.sh`) replaces entitlements with the provisioning profile's, whose group IDs we don't control, so both processes parse their `embedded.mobileprovision` and deterministically pick the same group (preferred if granted, else first sorted). The publish password keychain item uses `kSecAttrAccessGroup` = that group, with an ungrouped fallback for builds with no app-group entitlement (simulator).
- **`build-and-sign.sh` must never override `PRODUCT_BUNDLE_IDENTIFIER` on the xcodebuild command line** — command-line settings hit every target, cloning the app's ID onto the appex → installd `DuplicateIdentifier` (error 3002). The script patches each bundle's Info.plist after unpacking instead (app = `BUILD_BUNDLE_ID`, appex = `.broadcast` suffix), embeds the profile in both bundles, and signs the appex (inside-out) before the app.
- Tab-side capture pauses when the app loses foreground; the extension does not (separate process).
- **TLS**: a non-empty `broadcast.certFingerprint` (hex DER-SHA256, set by the pairing URL) switches `RTSPPublisher` to RTSPS with a custom `sec_protocol_options_set_verify_block` — system trust is fully replaced by the fingerprint match. The companion's managed mediamtx config is `rtspEncryption: strict`, so plain-RTSP clients can't connect to a companion-configured server.
- The companion's `BroadcastServerManager` shells out to `/usr/bin/openssl` (LibreSSL — RSA keygen for compat) and `brew services`; it requires the companion to be **unsandboxed** (it is) and mediamtx installed via brew (`/opt/homebrew` or `/usr/local` prefix).
- **"Add Sources to OBS"** (`OBSWebSocketClient`, obs-websocket v5 on `ws://127.0.0.1:4455`) provisions both Browser Sources in the current scene. The WebSocket password is picked up from the clipboard if the field is empty (the documented flow: OBS → Tools → WebSocket Server Settings → Show Connect Info → Copy Password; the user must press **Apply** after enabling the server or the password isn't saved) and persisted in UserDefaults on success. Source settings: `?controls=false&muted=false` URLs (a muted page produces **no** audio), `reroute_audio: true` (= the "Control audio via OBS" checkbox, required for mixer audio), `shutdown: true` (hidden sources release their WHEP connection). Layout is **enforced on every run** (existing sources get `SetInputSettings` + `SetSceneItemEnabled`/`SetSceneItemIndex`): camera on top + visible, view hidden — both are full-canvas and a dead WHEP page draws an opaque "stream not found" error that would cover the other source.

## SSH / Remote Claude / Companion Injection

- **macOS Keychain is unreachable over SSH** (it's bound to the GUI login session). Fix: a long-lived token stored in the Vision Pro keychain (`KeychainStore`) **per connection AND per agent** and injected per session as the agent's env var. Keychain account scheme: Claude keeps the bare connection UUID (so tokens stored before multi-agent support survive untouched), Copilot/Custom are suffixed `.<agent>`.
- **Claude tokens are minted in-app too, and `setup-token` is deliberately not used.** `ClaudeOAuth` runs Claude Code's own authorization-code + PKCE flow inside a `WKWebView` (`ClaudeLoginSheet`). The reason for the whole exercise: the CLI passes `inferenceOnly` for `setup-token`, narrowing the grant to `user:inference`, and **without `user:profile` an agent can't read the account's model entitlements** — it can't tell which models the plan covers. This flow requests the full session set instead (`user:profile`, `user:inference`, `user:sessions:claude_code`, `user:mcp_servers`, `user:file_upload`; `org:create_api_key` intentionally omitted). Sharp edges, all verified against the 2.1.222 binary rather than docs:
  - **The redirect target is `http://localhost:3118/callback`**, a loopback URL only the CLI listens on. Nothing listens here — the `WKNavigationDelegate` intercepts the navigation and `.cancel`s it, reading `code`/`state` out of the URL. That's why it must be an embedded web view and not `ASWebAuthenticationSession`, which can't intercept an `http://` callback.
  - **The token endpoint takes JSON**, not form encoding. A form body is rejected.
  - **Refreshes must re-send the full `scope` list** or the new token silently drops `user:profile` (the current CLI sends it for the same reason).
  - **Full scopes and a custom expiry don't combine, and asking is fatal rather than merely ignored.** Sending `expires_in` (what `setup-token` does for its one-year token) is rejected with `HTTP 400: custom expires_in not allowed for scope user:mcp_servers` — so it doesn't downgrade the token, it breaks sign-in. Note the restriction is pinned to a **specific scope**, not to long lifetimes in general, so the CLI's "long-lived tokens are limited to inference-only" string undersells it. Full-scope tokens take the server default (~8h); `resolvedSSHEnvironmentRenewingCredentials(for:)` refreshes right before each launch and the tmux idle reaper clears sessions that outlive one. `ClaudeOAuthTests` asserts neither grant body carries `expires_in`. Granted scopes still come from the **response**, never inferred from the request.
  - **Cookies persist, and that isn't a user-facing choice.** `ClaudeLoginSession` uses a persistent store so signing in again skips the emailed code. The claude.ai session cookie *is* a credential, but it lives in the app container on visionOS — sandboxed and encrypted at rest, exactly what the keychain credential already relies on — so there's nothing to decide. Contrast the **refresh token**, which is opt-in precisely because it leaves the headset for a macOS process environment that anything running as the same user can read. Don't collapse the two: same secret class, different partitions.
    - It's a **dedicated identified store** (`WKWebsiteDataStore(forIdentifier:)`), not `.default()`, so Claude's cookies don't mix with other web content and can be deleted precisely. The identifier must not be the all-zero UUID — WebKit throws.
    - Swift names are non-obvious: the ObjC factory `dataStoreForIdentifier:` imports as the **initializer** `WKWebsiteDataStore(forIdentifier:)`, and `removeDataStoreForIdentifier:completionHandler:` imports as `remove(forIdentifier:)` (the redundant `DataStore` is stripped) with an async variant. Neither is `dataStore(forIdentifier:)`/`removeDataStore(...)`.
    - Signing out deletes the store — revoking a credential while leaving the browser cookied would mean "sign out" still left a way straight back in. WebKit requires no live `WKWebView` hold the store during removal, so deletion only happens from the setup sheet with the login window closed.
  - The web view sets a desktop-Safari UA, without which federated identity providers refuse to render a sign-in form in an embedded view.
  - **Claude's login emails a code *and* a magic link, and neither reaches the web view on its own.** Tapping the link opens Safari, which has a separate cookie jar (doubly so here — this store is non-persistent), so the user gets signed in somewhere the sheet can't see while the consent page sits waiting forever. `ClaudeLoginSheet` therefore watches the clipboard and brings back whichever the user copied: a code is typed into the form, a link is loaded in **this** web view. Typing the code goes through `HTMLInputElement`'s native value setter plus synthetic `input`/`change` events, because the page is React and would discard a plain `.value` assignment on its next render. Only `changeCount` (a counter) is polled and `detectPatterns` classifies without disclosing — the actual read happens on tap, which is also what makes the system paste notification expected. Clipboard URLs are host-checked against Claude's domains before loading; the sheet shows a lock and hostname, and following an arbitrary copied URL would make that reassurance a lie.
  - **The token alone is not enough — injecting only `CLAUDE_CODE_OAUTH_TOKEN` silently downgrades the session.** When the CLI authenticates from the environment it cannot introspect the token, so it builds its credential as `scopes: CGp()` — and `CGp` **defaults to `["user:inference"]`** — with `subscriptionType: env.CLAUDE_CODE_SUBSCRIPTION_TYPE || null`. A full-scope token therefore presents as inference-only with no plan: the header prints `Claude API` (the `default:` branch of the tier switch, *not* a cosmetic label) and models included with the subscription ask for separately-purchased usage credits. Three more variables are required, all set by `Credential.sessionEnvironment(includeRefreshToken:)`:
    - `CLAUDE_CODE_OAUTH_SCOPES` — space-separated, and it must report what the server **granted**, not what was requested.
    - `CLAUDE_CODE_SUBSCRIPTION_TYPE` — `max`/`pro`/`team`/`enterprise`, obtained by fetching `GET https://api.anthropic.com/api/oauth/profile` and mapping `organization.organization_type` (`claude_max` → `max`, etc.). `/login` does this fetch itself and persists the result next to the token; an env-var session has no persisted profile, so this app fetches it at sign-in. Omitted entirely when unknown — the CLI treats `""` as a value.
    - `CLAUDE_CODE_RATE_LIMIT_TIER` — optional, from the same profile.
  - **`CLAUDE_CODE_OAUTH_REFRESH_TOKEN` exists**, and with it the CLI renews its own credential instead of being bounded by one access token's ~8h life. It **requires** `CLAUDE_CODE_OAUTH_SCOPES` (the CLI errors out otherwise). Gated behind `SavedConnection.sshInjectClaudeRefreshToken`, **default off on purpose**: an access token expires in ~8h, which bounds the damage if anything on the host can read a process's environment, and a refresh token carries no such bound. Off is also why `staleSessionTTLSeconds` must stay under the token life; if this is ever defaulted on, revisit that.
  - **A pasted token deliberately gets none of this extra context.** It's most likely a `setup-token` credential that genuinely is inference-only, and asserting scopes it lacks would be a lie the CLI acts on.
  - **Everything version-sensitive lives in `ClaudeOAuth.Constants`** because it's an unsupported surface an upstream CLI release can move. Re-extract with `strings -n 6 <binary> | grep -oE '.{600}CLIENT_ID:"[0-9a-f-]{36}".{500}'`.
- **Copilot tokens are minted in-app, not pasted.** `GitHubDeviceFlow` runs GitHub's OAuth device-authorization flow from the headset (Copilot CLI is a public GitHub App client — no secret): `POST /login/device/code` → show `user_code` + `verification_uri` natively → poll `POST /login/oauth/access_token` (honoring `authorization_pending`/`slow_down`) → store the `access_token`. Client ID: `Ov23ctDVkRmgkPke0Mmm`, scope: `read:user,read:org,repo,gist`.
- **Idle teardown: `TMOUT` cannot close an agent session, and the app-side reaper alone doesn't either.** Both verified on tmux 3.7b against real sessions:
  - When a command is passed to `tmux new`, **the pane process is that command** — `pane_current_command` reads as the `claude` binary, not a shell. `TMOUT` is a *shell* feature that only fires at an interactive prompt, so it is structurally incapable of closing a managed agent session. It still earns its keep for `persistentShellCommand` with an empty launch (a real shell), and nowhere else.
  - `reapStaleSessions` only runs **when the app connects**, so nothing collected abandoned sessions while the headset was off. Observed live: app-tagged sessions still running after 13h, 14h and **88h** detached, against a 12h TTL. The selection logic was correct all along — nothing was calling it.
  - Fix: `reaperWatchdogCommand` starts a detached, **untagged** `longwave-reaper` tmux session that reaps on an interval and `exit 0`s once no tagged sessions remain. `tmux new -A` is the entire concurrency story — attach-or-create can't duplicate and transparently restarts a dead watchdog, so there's no lockfile or pidfile and nothing is written to the host's disk. Started from `sessionOptions`, so both launch and re-attach install it.
  - The script is **base64'd** because it must survive three quoting layers (`zsh -lic '…'` → `tmux new … sh -c "…"` → the loop). Encoded it contains no `'` or `$` for an outer shell to expand — a test asserts that.
  - `session_activity` is the idle signal and it is sound: it advances on pane *output*, and an agent idle at its prompt is silent (confirmed by the 13h/14h/88h sessions above having stopped climbing).
  - **`staleSessionTTLSeconds` (6h) is deliberately under a full-scope Claude token's ~8h life** and no longer aliases `promptIdleTimeoutSeconds`. A token is injected once into the agent process's environment, and a running process's env can't be rewritten — so re-attaching a session whose token expired yields an agent that can't authenticate and can only be fixed by restarting it. Reaping first means a stale session is *gone* rather than *broken*.
- **No `sshd_config` / `AcceptEnv` dependency** (rejected as macOS-update-fragile). The token is baked **inline** into the launch command by `SSHTerminalManager.claudeCommand`: `tmux set -gqa update-environment NAME; NAME=<tok> tmux new -A -d -s slug -c dir claude --allow-dangerously-skip-permissions; exec tmux attach`. `exec` sheds the token-bearing argv within ms; `update-environment` makes it reach a pre-existing tmux server (session-scoped).
- **Managed Claude sessions launch with `--allow-dangerously-skip-permissions`, never `--dangerously-skip-permissions`.** The two are one word apart and do different things: the `--allow-` form only makes bypass-permissions *selectable* in the Shift+Tab cycle and leaves the session in Claude's normal default mode, while the bare form starts it in bypass. Approving prompts through a floating headset terminal is the worst part of driving an agent from Vision Pro, so bypass is one keystroke away — but no session starts unguarded on the user's behalf. The flag lives in `SSHAgent.defaultFlags` and is composed by `defaultLaunchCommand`, so it applies to the built-in Claude agent only; `.custom` is a command line the user owns and is passed through verbatim. `SSHTerminalManagerTests` asserts the bare form and any `--permission-mode` override never reach the launch line. It is a CLI flag, so it's an upstream-movable surface like the rest of `ClaudeOAuth` — a host with a `claude` older than ~2.1.14x predates it and would exit on the unknown option.
- **Secure Enclave key**: `SecureEnclaveSSHKey` (P-256, `ecdsa-sha2-nistp256`); falls back to a software P-256 key in the Keychain on the simulator. Host keys are accepted TOFU (pinning is a TODO).
- **Companion text injection is text-only by design**: `Shared/CompanionInjectProtocol.swift` can express only `injectText` (UTF-8) and `injectBackspace` (count) — never key codes or modifiers — so a compromised channel can't synthesize Cmd+Space/Run-dialog payloads. The channel is TLS-1.2-PSK on port 4856 via `CompanionInjectCrypto` (same companion token as audio, **domain-separated** HKDF).
- `SavedConnection.linkedCompanionConnectionID` (renamed from `linkedAudioConnectionID`, `@Attribute(originalName:)`) links a VNC connection to a companion (audio) connection.
- SSH sessions persist via tmux (`new -A`); a closed/wedged session is revived with `SSHSession.restart()` (Reconnect button).

## Logging

- visionOS app logs via `AppLog` (`os.Logger`, one category per component, `.line()` helper marks messages `.public` so OSLogStore shows them un-redacted — never use for secrets). `LogStore` polls the process-scoped OSLogStore (~1 s, viewer-refcounted, only while a Console view is visible).

## General

- **visionOS targets are arm64-only** (`ARCHS = arm64` in project-level build configs). Caveat: SPM packages do NOT inherit project build settings, so `-destination 'generic/platform=visionOS Simulator'` still builds Opus for x86_64 and fails. Use a concrete simulator destination (`platform=visionOS Simulator,name=Apple Vision Pro`, builds active arch only) or pass `ARCHS=arm64` on the xcodebuild command line.
- **The macOS targets are universal binaries** (`ARCHS = "arm64 x86_64"`, overriding the project-level arm64-only default). The `ci/patches/opus-x86_64-universal.patch` guards ARM NEON intrinsic sources behind arch checks.
- **The Opus package must NOT ship a custom `include/module.modulemap`** — Xcode auto-generates an umbrella-header modulemap for the target (`opus.h` matches the module name `Opus` case-insensitively), so a hand-written `umbrella "."` map double-covers `include/` and Xcode 26.6+'s clang dependency scanner fails every scan with "umbrella for module 'Opus' already covers this directory". `setup-deps.sh` no longer installs one and deletes it from existing checkouts; if the error reappears, check for a stray `repos/opus/include/module.modulemap` and stale `build/DerivedData`.
- **SwiftData migrations** require default values on all new non-optional properties and `@Attribute(originalName:)` for renamed columns, or the store fails to load (CoreData error 134110).
- **`navigationTitle` requires `NavigationStack`** on visionOS — without it, the title bar doesn't render.
- **`dismissWindow(id:)`** is the correct API for closing `WindowGroup` windows on visionOS, not `dismiss()`.
- **`UIKey.characters`** is `String` (non-optional) in this SDK version, not `String?`. Use `.isEmpty` checks instead of optional binding.
- **A hardware-keyboard capture surface may hold first responder only while nothing in the app is entering text**, and every window has its own first responder — so "don't take it" is only half the rule. `KeyCaptureResponderView` (VNC/Moonlight/Native) and `VisionTerminalView` yield on `.textEntryDidBegin` and reclaim on `.textEntryDidEnd`; both edges come from `TextInputActivity`'s poll. Two traps behind this: `becomeFirstResponder()` also makes the view's *window* key, so a capture surface that keeps the responder keeps the keyboard away from a text field in another window entirely (that is how typing into "Add Connection" ended up in an open session); and the reclaim afterwards must check the key window, or finishing a form yanks focus back to the stream. `isKeyWindow` is frequently false for every window on visionOS, so gate on "some *other* window claims it", never on "this one does". Moonlight's `GCKeyboard` handler bypasses the responder chain altogether and needs the text-entry guard applied directly.
